# Requirements Document

## Introduction

Today, `reset_game` (`supabase/migrations/0005_rpc_lifecycle_and_claims.sql`) hard-deletes `winners`, `claims`, `marks`, `tickets`, `players`, and `called_terms` for the current game and rewinds that same `games` row to `LOBBY`, so every winner record from a completed session is permanently lost the moment the Host resets for the next round. Separately, both Host Dashboard and Presentation View resolve "the game to show" via `get_or_create_game(SEED_GAME_CODE)` — a fixed seed code lookup that has no notion of "the currently live game" distinct from "whichever row happens to match that code" and provides no way to atomically hand every connected screen a brand-new game identity on reset.

This module introduces two capabilities on top of Module 6's Supabase-backed architecture:

1. **Persistent winner history.** Winner records survive `reset_game` forever and become visible, Host-side only, as a complete history spanning every past game — not only the currently active one.
2. **A server-side active-game pointer with code/QR rotation on reset.** Host Dashboard and Presentation View stop resolving "the game" by seed code and instead resolve it through a genuine, singleton, server-side pointer. Resetting the game atomically retires the old game, creates a new game row with a freshly generated code, and repoints that pointer to the new game — and every already-open Host and Presentation tab picks up the new game automatically over its existing Realtime subscription, with the old game's subscription torn down cleanly. Player Join is explicitly excluded from pointer-following: it continues to require a typed/scanned code, exactly as today.

This module is additive on top of Module 6's schema, RPCs, RLS posture, and Realtime wiring and must not regress any existing Module 6 behavior — in particular the tested invariant that Presentation View never exposes a Player's Employee/Demo ID (`PresentationView.test.tsx`, "PresentationView never exposes an Employee/Demo ID (Req 17.3)") continues to hold for both the live game view and any winner-related display this module adds to Presentation View (none is added; winner history is Host-only). This module does not introduce Supabase Auth, a UI redesign beyond what these two capabilities require, or any change to Player Join's code-entry requirement.

## Glossary

- **System**: The Cyber Tambola V2 application as extended by this module, spanning its React/TypeScript client and its Supabase (Postgres + Realtime) backend.
- **Backend**: The Supabase project's Postgres database, its RPC functions, and its Realtime layer.
- **Game**: A row of the existing `games` table (per Module 6), identified by its `id` and unique `code`.
- **Winner**: A row of the existing `winners` table (per Module 6), recording one confirmed prize claim for one `(game_id, prize_id)` pair.
- **Winner_History**: The complete set of Winner rows across every Game that has ever existed in the Backend, independent of whether that Game is the Active_Game or has since been reset.
- **Active_Game**: The single Game that the Backend designates, via the Active_Game_Pointer, as the one Host Dashboard and Presentation View SHALL resolve to and follow.
- **Active_Game_Pointer**: A singleton server-side record identifying, at any moment, at most one Game as the Active_Game.
- **Reset**: The host-only operation, invoked from Host Dashboard, that ends the current Active_Game's session and establishes a new Game as the Active_Game.
- **New_Game_Code**: The unique `code` value generated by the Backend for the Game created during a Reset, distinct from every `code` value ever previously generated.
- **RPC**: A Postgres `SECURITY DEFINER` function callable from the Client via `supabase-js`, gated by `host_secret` for any host-only action, per Module 6's established convention (Requirement 10 of `module-6-realtime-multi-device-sync`).
- **Realtime_Subscription**: A Client's `postgres_changes`-based subscription to row changes on one or more Backend tables, per Module 6's established convention.
- **Host Dashboard**: The Host-facing screen (`src/pages/HostDashboard/HostDashboard.tsx`).
- **Presentation View**: The projector-facing screen (`src/pages/PresentationView/PresentationView.tsx`), which never displays a Player's Employee/Demo ID.
- **Player Join**: The join screen (`src/pages/PlayerJoin/PlayerJoin.tsx`), which requires a typed or scanned Game code and does not follow the Active_Game_Pointer.
- **Local_Fallback**: The existing no-Supabase-configured dev mode (Module 6 Requirement 17), in which the System runs entirely off client-local state with no Backend.

## Requirements

### Requirement 1: Winner rows are never deleted by Reset

**User Story:** As a host running multiple back-to-back game sessions, I want every winner from a completed session to remain permanently on record when I reset for the next session, so that I never lose the names, ticket references, and prizes I already awarded.

#### Acceptance Criteria

1. WHEN a Reset is performed, THE System SHALL leave every existing Winner row for the previous Active_Game unmodified and undeleted.
2. THE System SHALL scope Reset's deletions to only `claims`, `marks`, `called_terms`, `tickets`, and `players` rows belonging to the previous Active_Game, and SHALL NOT delete any `winners` row as part of Reset.
3. FOR ALL Games that have ever been created by the Backend, THE System SHALL retain that Game's own `winners` rows indefinitely, independent of whether a subsequent Reset has since made a different Game the Active_Game.
4. THE Backend SHALL continue to enforce, at the database level, that at most one Winner row exists per distinct `(game_id, prize_id)` pair, unchanged from Module 6 Requirement 1.7.

### Requirement 2: Host Dashboard shows a complete, read-only winner history across all games

**User Story:** As a host, I want to see every winner from every game I've ever run, grouped by session, so that I can review past sessions without needing to have kept a separate record myself.

#### Acceptance Criteria

1. THE Host Dashboard SHALL display a Winner_History section listing every Winner row across every Game recorded by the Backend.
2. THE Host Dashboard SHALL group the Winner_History section's entries by their owning Game, and SHALL order those groups with the most recently created Game first.
3. FOR EACH Winner_History entry, THE Host Dashboard SHALL display, at minimum, the prize label, the winning Player's display name, the winning Ticket's reference, and the confirmation timestamp.
4. THE Host Dashboard SHALL label each Winner_History group with that group's Game code and creation timestamp, so that entries from different sessions are visibly distinguishable.
5. THE System SHALL NOT display the Winner_History section, or any part of it, on Presentation View.
6. THE Host Dashboard SHALL update the Winner_History section automatically via the Realtime_Subscription mechanism when a new Winner row is created for any Game, without a manual refresh.
7. THE System SHALL NOT display a Player's Employee/Demo ID anywhere within the Winner_History section.

### Requirement 3: A genuine server-side pointer determines the Active_Game

**User Story:** As a developer preventing a stray test game from hijacking the live presentation, I want the Backend to track exactly one designated "current" game through an explicit mechanism, not by guessing by recency, so that Host Dashboard and Presentation View always show the game the host actually intends.

#### Acceptance Criteria

1. THE Backend SHALL define an Active_Game_Pointer mechanism that identifies at most one Game as the Active_Game at any moment.
2. THE System SHALL NOT resolve the Active_Game by selecting the most-recently-created Game row or by any other recency-based inference; resolution SHALL be through the Active_Game_Pointer only.
3. WHEN the Backend is queried for the Active_Game and the Active_Game_Pointer designates a Game, THE System SHALL return that designated Game.
4. IF the Active_Game_Pointer designates no Game, THEN THE System SHALL report that no Active_Game currently exists, rather than falling back to any other Game selection method.
5. THE Backend SHALL enforce, at the database level, that the Active_Game_Pointer mechanism can designate at most one Game as the Active_Game at any moment.

### Requirement 4: Host Dashboard and Presentation View resolve and follow the Active_Game

**User Story:** As a host, I want the dashboard and the projector screen to always be looking at the same live game, so that I don't have to manually keep two devices in sync.

#### Acceptance Criteria

1. WHEN Host Dashboard mounts with Backend configuration present, THE System SHALL resolve the Active_Game via the Active_Game_Pointer and establish a Realtime_Subscription scoped to that Game's `id`.
2. WHEN Presentation View mounts with Backend configuration present, THE System SHALL resolve the Active_Game via the Active_Game_Pointer and establish a Realtime_Subscription scoped to that Game's `id`.
3. IF no Active_Game exists at the time Host Dashboard or Presentation View mounts, THEN THE System SHALL display a state indicating no active game exists, and SHALL NOT display stale data from any previously resolved Game.
4. WHILE Host Dashboard or Presentation View holds no Active_Game, THE System SHALL continue observing Active_Game_Pointer changes such that a subsequently designated Active_Game is picked up without a manual page reload.

### Requirement 5: Reset atomically retires the old game and activates a newly created one

**User Story:** As a host wrapping up one session and starting the next, I want a single Reset action to close out the old game, spin up a fresh one with its own code and QR target, and make it live everywhere, so that I don't have to coordinate multiple manual steps.

#### Acceptance Criteria

1. WHEN the Host triggers Reset, THE System SHALL, within one RPC invocation, create a new Game row with a newly generated New_Game_Code and update the Active_Game_Pointer to designate that new Game, such that both effects are visible together or neither is visible.
2. THE System SHALL generate each New_Game_Code as a value distinct from every `code` ever previously generated for any Game.
3. THE New_Game_Code SHALL follow the existing `games.code` format convention (an uppercase alphanumeric string, consistent with the `CYBER24`-style `SEED_GAME_CODE` convention already in use).
4. WHEN Reset creates a new Game, THE System SHALL initialize that Game's `status` to `LOBBY`, consistent with the default state of a freshly created Game.
5. THE System SHALL require a Host_Secret argument for the Reset RPC, checked against the previous Active_Game's stored `host_secret`, consistent with every other host-only RPC established in Module 6 Requirement 10.
6. IF the Reset RPC is invoked with a Host_Secret that does not match the previous Active_Game's stored `host_secret`, THEN THE System SHALL reject the invocation and SHALL NOT create a new Game or modify the Active_Game_Pointer.
7. WHEN Reset completes, THE System SHALL retain the previous Active_Game's row and its Winner rows in the Backend, per Requirement 1, and SHALL NOT delete that Game row.

### Requirement 6: Already-open Host and Presentation tabs follow the Active_Game change live

**User Story:** As a host, I want my already-open dashboard tab and the projector's already-open presentation tab to switch to the new game automatically the moment I reset, so that nobody has to refresh a screen mid-event.

#### Acceptance Criteria

1. WHEN a Reset changes which Game the Active_Game_Pointer designates, THE System SHALL cause every open Host Dashboard and Presentation View Client to detect that change via the Realtime_Subscription mechanism, without a manual page reload.
2. WHEN a Host Dashboard or Presentation View Client detects an Active_Game_Pointer change, THE System SHALL tear down that Client's Realtime_Subscription scoped to the previous Game's `id` before or as part of establishing a new Realtime_Subscription scoped to the new Game's `id`.
3. AFTER a Host Dashboard or Presentation View Client has switched its Realtime_Subscription to the new Game's `id`, THE System SHALL NOT apply any further event originating from the previous Game's `id` to that Client's displayed state.
4. WHEN a Host Dashboard or Presentation View Client switches to the new Active_Game, THE System SHALL replace that Client's displayed game state (game code, status, current word, revealed terms, claims, winners) with the new Game's own state, and SHALL NOT display any residual state from the previous Game.
5. THE System SHALL propagate an Active_Game_Pointer change to connected Host Dashboard and Presentation View Clients through the Realtime_Subscription mechanism, not through Client-side polling.

### Requirement 7: Player Join continues to require an explicit code and never follows the Active_Game_Pointer

**User Story:** As an employee joining the game, I want to keep entering or scanning the code shown on the projector, so that I always join the specific session the host intends, even if I have an old tab or bookmark open.

#### Acceptance Criteria

1. THE System SHALL continue to require Player Join to resolve a Game only via a Client-submitted Game code, unchanged from Module 6 Requirement 3.1.
2. THE System SHALL NOT cause Player Join to resolve, prefill from, or automatically follow the Active_Game_Pointer.
3. WHEN the Active_Game_Pointer changes, THE System SHALL NOT cause a Player Join screen already open in a browser tab to change its submitted or displayed Game code as a result.
4. THE System SHALL continue to reject a Player Join attempt whose submitted Game code does not match any existing Game, unchanged from Module 6 Requirement 3.2.

### Requirement 8: QR code and join instructions reflect the current Active_Game's code

**User Story:** As a host, I want the QR code and join instructions on the projector to always point to whichever game is currently active, so that a scan always lands on the live session, not a retired one.

#### Acceptance Criteria

1. WHILE Presentation View holds an Active_Game, THE System SHALL render the QR code and join instructions using that Active_Game's own `code`.
2. WHEN Reset changes the Active_Game, THE System SHALL cause Presentation View's displayed QR code and join instructions to update to the new Active_Game's `code` via the Realtime_Subscription mechanism, without a manual refresh.

### Requirement 9: Local Fallback dev mode retains equivalent reset and history behavior without a Backend

**User Story:** As a developer running the app without Supabase configured, I want winner history retention and active-game rotation to still behave sensibly in local-only mode, so that the dev/demo experience does not regress.

#### Acceptance Criteria

1. WHERE Backend configuration is absent, THE System SHALL retain every previously accumulated Winner entry in the Local_Fallback client-local state across a Reset, rather than clearing it.
2. WHERE Backend configuration is absent, THE System SHALL make the Host Dashboard's Winner_History section display every retained Winner entry grouped by the client-local session they belong to, consistent with Requirement 2's grouping and ordering.
3. WHERE Backend configuration is absent, WHEN Reset is triggered, THE System SHALL generate a new client-local Game identity and New_Game_Code for that session, following the same New_Game_Code format convention as Requirement 5.3, and SHALL make that new Game the one reflected by Host Dashboard and Presentation View.
4. WHERE Backend configuration is absent, THE System SHALL NOT display the Winner_History section on Presentation View, consistent with Requirement 2.5.
